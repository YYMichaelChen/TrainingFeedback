## 1. 准备材料

在构建机为审核建立一个新的隔离数据根和独立 locator，通过现有应用的
“设置 → 导出全部训练证据”生成 JSON 和 Markdown。可用现有
`ApplicationContext.create(path, Locator(locator_path))` 与
`HandoffService(...).export()` 做相同的本地准备；始终显式指定隔离路径，关闭上下文后再复制根。

使用正常种子内容：36 项指导均为未审核，初始计划为 draft，无使用版本指针、
实际训练、外部审核或用户确认事实。不能使用打包验收 fixture：其中包含软件测试专用的合成审核和训练记录。

本地审核包提供：

| 文件 | 用途 |
| --- | --- |
| `README.md` | 提交顺序、材料性质和后续操作。 |
| `evidence.json` / `evidence.md` | 同一次现有导出产生的完整数据与可读正文。 |
| `material-manifest.json` | 应用/源码身份、导出时间、内容版本、文件大小与哈希。 |
| `review-request.md` | 可直接交给外部 AI 的审核请求。 |
| `review-checklist.md` | 先 13 项计划内动作、后 23 项其余动作的逐项回传表。 |
| `plan-response.schema.json` | 从 evidence 中原样提取的 plan v1 schema。 |
| `plan-response.format-example.json` | 完整复述种子提案的格式演示；不是审核意见或已批准训练方案。 |
| `verification.json` | 结构、状态、正文一致性及隔离导入检查结果；不是专家审核结论。 |

JSON/Markdown 中的原始文本保持原样。说明、版本清单和格式演示通过独立文件提供。
这些包及验证根保存于本地任务材料目录；权威内容与实际个人证据各自保留在原来的位置。

## 2. 提交外部审核

由用户自行把 `review-request.md`、`evidence.json`、`evidence.md`、
`review-checklist.md` 和 `plan-response.schema.json` 交给所选择的外部 AI。
需要格式参考时再附带明确标识的 format-example。

审核请求必须说明：

1. 材料来自未审核种子；零会话不代表用户从未训练。指导中的预期感受、常见代偿、停止标准均不是用户症状或经历。
2. 优先审核初始计划引用的 13 项，随后完成其余 23 项；最终覆盖全部 36 项。
3. 逐项检查目的、主要/次要部位、起始姿势、步骤、呼吸、节奏、预期感受、常见代偿、停止标准、进退阶、器械、适用性、注意事项和图片缺失状态。
4. 分开说明结构完整性与内容判断，检查字段之间是否一致；有依据的修订说明依据及来源，无法确定的内容明确保留问题。
5. 整体计划检查动作顺序、阶段、全部逐组剂量/单位/每侧标记及休息。材料不包含个人病史、能力或实际反馈；需要这些信息才能判断的事项列为待补充，不自行假设。
6. 回传动作名称和材料版本、审核结论、具体问题、建议修改及依据；不得在应用数据中代填用户批准或已启用状态。

实际审核后，保存外部原始答复及其来源、实际发生时间。收到答复表示收到意见；
不自动代表全部指导已通过审核。逐项状态使用“可进入用户复核”“需修改后复审”或“信息不足”。

## 3. 回传计划文件

沿用 `training_feedback.plan`、`schema_version: 1`。以当前导出的
`plan_import_schema` 为唯一格式来源，不另建一套兼容协议。

- 提供非空 `rationale`，说明实际调整理由与证据；格式演示的理由不能作为真实意见。
- `plan` 提供完整名称、目的和训练日；每个训练日提供全部动作，每个动作提供全部组及剂量。
- 明确动作名称、顺序、阶段、休息、组顺序、数值、单位、每侧标记和原始备注，不能只回传改动片段。
- 修订已有计划时，核对目标根中的 `target_plan_name`。省略该字段表示创建新计划，不能用格式演示的名称修订真实计划。
- `source.session_id`、`source.export_id` 属于产生它们的数据根。准备包来自隔离根，数字相同也不能认定为真实根中的同一对象。

实际导入前先从**目标用户根**重新导出，明确正在审核的内容版本和计划。
让外部答复引用该导出及确实存在的来源；初次计划不存在训练会话时，session_id 保持 null。
纯格式示例的两个来源字段均为 null。不要把准备包的 ID 粘贴进另一数据根。
示例只能在隔离验证根中导入；应用校验通过也不证明跨根来源语义正确。

## 4. 应用真实审核结果

0.6.1 起，动作库有两条互不干涉的状态轴：指导版本「已审核/未审核」，动作「启用/未启用」；
另外每个动作单独指向一个「使用版本」。审核不会自动启用动作，启用也不代表已审核；
未审核的指导可以设为使用版本、可以进入已启用计划并训练，激活预览会逐项列出未审核动作，
训练记录也会冻结执行当时的审核状态。因此下述步骤记录的是真实审核事实，不是解锁训练的开关。

1. 对照内容标识、版本和正文核对收到的答复。若当前目标版本已变，重新核对或复审；不能把旧意见当成新文本的审核。
2. 指导有修改时，在动作编辑器保存为新版本，保留未编辑文本和已有历史。新版本是未审核的，
   也不会自动成为使用版本；对新文本完成必要的复审，再打开明确选中的版本。
3. 在“记录动作指导的外部审核”中阅读完整正文与差异，填写实际外部审核来源和备注，
   在“外部审核发生时间”中填入实际日期或带时区时间，例如
   `2026-09-12` 或 `2026-09-12T09:30+08:00`。只知道日期就只填日期；
   不知道时保留为空并等待补充，不以提交时刻代替。字段默认为空且不会自动填入。
   0.5.1 起可用“今天”“此刻”“沿用上次”一键填入，填入后仍可修改；点击即表示这是
   你确认的发生时间，同一次审核跨多次批准应使用“沿用上次”保持一致。
   0.5.0 起可另选“审核答复原件”，应用把原件复制进数据根 `reviews/` 并记录相对路径与
   SHA-256，随备份一同保留；备注仍可写明答复位置，但不再依赖手写路径。
   用户确认时间由应用在确认时单独生成。切换指导版本会清除本次输入和勾选，
   既有记录仍在只读正文中展示。0.3.0/0.3.1 表单的 `reviewed_at` 可能为提交时刻，
   旧值保持原样，解释其实际含义须查原备注和外部答复，不能推测性修正。
4. 用户明确勾选“这次外部审核确实针对当前显示的版本”后提交。表单默认勾选“同时设为使用版本”，
   取消勾选即只记录审核、不改使用版本。需要修改或信息不足的条目保持未审核，
   不填写虚构审核证据。同一次审核涉及多个版本时，可用动作库的“批量复核并批准指导…”：
   逐项勾选，默认全不勾，共享这一次审核的来源、时间与原件。
   已审核版本的审核字段不能原地改：发现填错就在详情页“撤销所选版本的审核”，
   清除这一版的审核证据（受管原件一并删除，使用版本与启用状态不变）后重新记录；
   已被训练记录引用的版本不允许撤销，只能另存新版本、对新文本复审。
5. 通过“训练计划 → 导入外部计划 JSON”保存计划草稿；0.4.0 自动打开该草稿。
   在版本选择器核对目标，阅读“完整处方”“与启用版本的差异”“导入时依据”。
   后续本地编辑不会改写原始导入文件或理由。所有编辑、指导审核和启用操作均
   针对当前所选版本；普通打开默认启用版本，没有启用版本时默认最新草稿。
   用户单独确认全部安排后再明确启用计划：启用要求每个动作已启用且其使用版本内容完整，
   未审核只在预览和确认里逐项提示，不阻止启用。
6. 导入和保存均不自动激活。准备包、外部审核、用户批准、计划确认分别记录状态。
   若版本在预览后已变化，重新打开、核对差异后再确认，不转而启用另一份草稿。

审核全部 36 项；用户批准实际所需指导，并单独确认计划。技术验收准备与内容审核可以并行。
W4 开始条件及至少三次真实会话和一次解释性修订闭环的要求，以开发计划为准。

## 5. 初始种子审核材料检查清单

- 36 项指导逐项完整，初始计划的 13 个动作均能解析；完整剂量来自种子，不重新手抄。
- 所有指导未审核、计划保持草稿，审核字段为空，没有真实训练或合成测试审核证据。
- JSON 与 Markdown 来自同一导出，内容可相互对应；内容身份和哈希可核验。
- 从 schema 派生的完整格式演示可解析，在另一个隔离副本中保存为草稿。
- 示例导入后，原指导、原计划和使用版本指针保持不变；验证副本不混入审核原始材料。
- 表格中的审核结论、实际来源/时间和用户批准在真实发生前均保留待处理状态。

独立 Windows 历史操作见 [packaged-acceptance-runbook.md](../0.6.0/packaged-acceptance-runbook.md)。

## 6. W4 真实使用与专家修订

所需动作已启用且使用版本完整、用户已确认完整计划并明确启用、适用程序版本的本机自检
已通过后，可以开始个人 W4。未审核指导在激活预览中逐项提示，不阻止启用；
审核覆盖按实际证据单独记录。0.6.0 的 Phase C 结果仅属于原候选程序，不能作为 0.6.1 的打包验收结果。
当前独立 8-B2 验收暂缓；它仍是扩大分发、增加用户和正式发布验收前的关卡。
W4 与完整 36 项种子审核各自按实际证据记录，不能由计划启用或材料准备推导完成。

将本节表格复制为数据根内 `reviews/w4-observation-<开始日期>.md`，由用户填写实际事实。
个人观察、外部答复、截图和导出均留在数据根，Git 只保留本手册的空白模板与非个人结论。
表格为空表示尚未记录；不知道的事实明确写“未知”，不能按模板、默认值或指导内容补成用户事实。

### 6.3 向外部专家交接并应用修订

1. 从目标用户根导出本次实际证据 JSON/Markdown，保存文件哈希与其中的 export ID。
   至少三次计入的真实会话、已知排除 ID 和次日反馈状态应与观察表对应。
   取同一 JSON 的 `plan_import_schema` 作为返回格式，不能用首次种子审核的隔离根 ID。
2. 用户将原始证据、计入/排除清单、实际操作或训练反馈，以及返回格式交给所选外部专家。
   明确未回答为未知、模拟记录不能支持实际训练结论，指导里的预期感受不是用户反馈。
   要求答复对具体会话、反馈和处方差异说明依据；信息不足时明确补充问题。
3. 保存真实答复原件、来源和实际发生时间。修订沿用第 3 节的 plan v1 完整计划格式，
   `rationale` 说明依据，`source.export_id` 对应目标根本次 JSON 的 ID；如填写 session ID，
   也须属于该根且符合实际引用。涉及多个会话时在理由中逐项说明，不发明新的格式字段。
4. 按第 4 节导入草稿，核对目标计划、完整处方、与启用版本的差异和导入依据。
   指导正文若有变化，新版本是未审核的，需要明确设为使用版本；先完成实际复审再启用最稳妥，
   但启用不强制已审核，激活预览会列出仍未审核的动作。最终由用户单独确认启用完整计划。
   外部答复、JSON 校验通过和保存草稿都不表示已获用户同意。
5. 启用后再导出一组证据，按第 6.4 节核对既有历史，并在闭环表记录新版本。
   若专家认为依据不足或无需修订，保留答复并继续观察，不为勾选完成而制造改版；修订闭环仍待完成。

### 6.4 历史核对与完成清单

对照修订前后的证据，以相同 session ID 核对既有会话：冻结的计划/动作/逐组处方、
结果与实际组、用户原文、事件、已有撤回审计均应保持完整，不能被新目录或新计划重写。
核对从实际反馈收集完成后的修订前导出开始；后续真实补交反馈或带审计的备注纠正，
应作为单独的用户操作解释，不能混作计划修订导致的历史变化。
导出时间/ID、新计划与指导版本、导入、审核和用户确认记录允许因本次流程新增；
不能用整个导出文件哈希相同作为历史不变条件。原始导出文件自身的哈希仍需保持不变。

- [ ] 基线可定位实际程序、启用计划和所需指导版本；模拟/合成 ID 已明确排除。
- [ ] 至少三次由用户确认的真实会话及保存结果可以核对。
- [ ] 次日反馈流程已有实际证据，未回答项仍为未知。
- [ ] 外部意见确实引用实际反馈，原件、来源和发生时间可追溯。
- [ ] 一次有真实依据的完整修订已导入、核对差异并由用户明确启用。
- [ ] 既有会话的冻结事实和原文保持完整，正常新增记录及实际用户纠正可分别解释。
- [ ] 已发现的软件问题完成复现记录，阻断问题修复并通过相关回归和打包检查。

全部具备实际证据后才能记录 W4 完成。空白模板、模拟自检和准备包不计入。
8-B2 仍单独记录为未执行，完整种子审核仍按实际逐项覆盖记录；W4 完成不等于正式发布验收完成。

### 7.1 升级后的材料定位

- 正常覆盖安装并打开原数据根后，由程序自动转换既有内容与设置；操作人无需接收内置草稿、
  手工匹配旧动作、重新导入计划或选择兼容模式。仍有效的既有确认不要求重复提交。
- 从正常动作详情核对 bundled/custom 来源、稳定键、目录版本、当前内容版本与图片哈希。
  程序内置正文/图片只读；用户覆盖、自定义内容与审核原件留在用户根。
- 旧审核记录保持其实际发生时的含义。缺少图片审核覆盖的旧证据不自动认证新图片；
  缺图/损坏图导致的当前不可用状态应指向具体补图问题，不提供旧规则开关。
- 审核材料由当前 v2 导出生成，附所需图片文件及相对路径/哈希。只给本机安装路径或
  `status: available` 不足以让外部审核者检查图像。历史材料的未知图片明确标注未知。

### 7.2 图片检查与真实审核

1. 准备完整正文和实际图片。缺图、占位、路径越界、无法解码或哈希不一致的内容保留草稿，
   可编辑、可阅读正文，但不可设为使用版本、启用或用于新开始的训练。
2. 对待审核的精确版本显示正文、步骤、图片及相对使用版本的变化；图像技术检查通过之后，
   再由实际审核者核对支撑点、活动侧、箭头、动作顺序以及图文是否一致。
3. 保留真实来源、实际发生时间、原始答复、内容/图片集合哈希及用户确认时间。
   不将图片存在、格式校验通过、安装包更新或用户点击启用解释为外部审核。
4. 正文或图片发生变化就创建新未审核版本；批量审核逐项选择准确目标并再次校验，
   任一项失败整批回滚。切换目标清空未提交输入，不把上一动作的意见自动套到下一动作。
5. 图片缺失会使当前有效审核/可用性失效，但原审核事件和历史训练快照仍保留；
   撤销也采用可追溯事件。修复同哈希资源不是一次新审核，不同图片不得沿用旧证据。

启用门槛采用开发计划第 12.4 节的统一表：无有效图为草稿且禁止启用；
完整正文和有效图、但无外部审核证据的版本，可按正常显式流程选用/启用，
在计划确认时明确列出未审核事实。审核与启用仍不得互相推导。

### 7.3 动作组计划与当前格式回传

- 0.7.0 只接受 `training_feedback.plan` v2 新导入，不再提供 v1 导入、版本选择或转换入口。
  使用同一次目标根导出内的当前 `plan_import_schema`；已存计划通过内部迁移保留，
  原始旧导入文件与旧导出文件保持原样。
- 回传完整计划：动作稳定引用、内容版本、动作组及组内顺序、每轮剂量、轮数、换侧方式、
  各层休息、转换说明和原始理由。不得只以“做三轮”省略每轮动作或每侧含义。
- 用“直腿后踢→消防栓”检查四点支撑连续例；若实际使用俯卧抬腿，则写明到四点支撑的体位转换。
  动作族相同或粗分类相同不能自动证明可以直接衔接。
- 导入只生成草稿；核对完整展开顺序与差异后再确认。激活绑定精确指导和图片，
  程序目录更新不能改写已确认处方；动作下架后更换动作必须走新草稿。
- 证据包中区分组汇总与逐轮成员的实际结果，避免把汇总再次计为训练量；
  单侧实际未记录不能补成双侧完成。所有未知项和用户原文继续原样保留。

### 7.4 删除审核与操作验收

070-F 已交付 schema21 和新模型动作库的「移除与恢复审核」入口，也可由
`LibraryContext.create_removal_page()` 组装；完整桌面路由和旧根自动转换仍属于 G。
在动作库选中一个或多个目标后打开审核页，新建申请，选择移除或恢复，填写原因，
预览全部内容身份和影响并明确提交。申请本身不改变可用性。

选中申请后预览当前影响，填写真实决定来源、实际发生时间及原文备注；
「填入我本人」「今天」「此刻」均需显式点击，默认不填写来源和实际时间。
进入审核后可以批准，或明确「批准并应用」；也可驳回、取消。
决定历史及此前影响依据始终保留。内容/选用版本改变须取消并重新申请；
引用影响变化须预览并「进入／刷新审核」后重新批准。失败不会清空未提交文字。

影响清单涵盖计划/组合、未结束和已结束会话、指导审核、依赖变体以及导出；
无法读取的既有导出保守列为「影响未知」。整批批准应用任一项失败全部回滚。
发行方目录记录单独显示目录版本、清单摘要和本机观察时间，不能本地恢复发行方撤回。
恢复不会自动启用动作，受影响的旧活动计划仍须创建并确认新修订后才能新开训练。

通过正常动作详情发起移除申请，检查目标内容身份和计划/动作组/会话/变式依赖清单。
填写实际理由并记录审核决定；同一用户可明确确认，不虚构外部审核者。
批准应用前重查内容与引用影响，目标改变时重新核对。内置动作的用户移除是根内决定，
不会修改程序动作库；发布方下架随新目录版本交付。

验收批准/拒绝/取消/恢复、批量失败回滚和目标变更；批准后不能用于新计划/新会话，
已暂停训练和历史仍依其冻结内容可用。不能连带删除变式、历史或原始导出。
恢复要重新满足当前图片/正文规则，并单独启用，不复活旧审核或旧设置。

记录每项实际结果：候选程序/目录/schema 身份、目标键/版本、操作、预期/实际结果、
证据路径与哈希。真实审核只记录真实发生的事实；合成回归材料必须标识为合成。
本节的空白要求不构成 0.7.0 内容审核、真实使用或打包验收完成证据。
