## 1. Identity, Content And Catalog

- Exercise reference: `{source: bundled|custom, key: stable-key}`. Names/aliases
  never replace stable identity. Custom copies receive their own identity; a
  supported migration allocates deterministic IDs and records mappings.
- Content reference: `{id, version, sha256}`. SHA-256 covers UTF-8 JSON with sorted
  keys, compact separators, unescaped Unicode and finite numbers. Arrays/text retain
  order and exact content; numeric representation (`1` vs `1.0`) affects hashing.
  `domain/catalog.py:content_sha256` is the serializer.
- The content envelope includes exercise reference, canonical name/aliases,
  category/equipment/body areas, family/variant/position and guidance without
  personal review. Images specify managed relative paths, required flags and hashes.
  Review, enablement and local IDs are separate root-local state.
- Catalog files, exact inventory, hashes and database metadata are verified read-only.
  Source resolution is package-relative and independent of cwd. No program journals
  or user overlays; fresh roots do not copy the full catalog into their database.
- New source additions/changes and real illustration bytes must be reproducible
  built-in catalog inputs under the latest rules. Current frozen 070-A
  [inventory](baseline/catalog-070-baseline.json) records 36 missing-image/unreviewed
  entries; it is baseline evidence, not a future catalog readiness claim.
- `snapshot-assets/` retains immutable hash-addressed content bytes and
  `custom-exercise-images/` holds root-local sources. Publish assets before committed
  references under the writer boundary; recover only unreferenced staged assets.

## 2. Plan V2 And Evidence V2

The [structural schema](plan-v2.schema.json) and [synthetic example](plan-v2.example.json)
define shape. Example zero hashes are placeholders, not resolver-valid content.
The packaged `training_feedback/contracts/plan-v2.schema.json` must match.
`PLAN_IMPORT_SCHEMA_VERSION` and `EVIDENCE_SCHEMA_VERSION` remain independent.
The [v1 snapshot](baseline/plan-v1-baseline.schema.json) is retained 0.7.0
contract evidence, not an accepted new-file format.

The root has schema/version, original rationale, optional source IDs and complete
plan. All object fields are declared; unknown approval/enablement/status fields,
duplicate JSON keys, nonfinite values and conflicting identities fail. Source IDs
belong to the target root: current session IDs refer to `group_session`, export IDs
to shared `group_plan_export` with session binding in `group_session_export`.

Days contain ordered standalone/group items. Item/member IDs are unique throughout
a revision and retained across clones; new items receive new IDs. Existing IDs must
match lineage. Orders are unique/positive within parents. Group members have no
independent phase and groups cannot nest. Same movement may occur in multiple items.
Each reference includes exact content/classification, dose sets, note and rest;
resolve against actual retained content instead of trusting supplied metadata.

One member has one unit and per-side convention across its sets. Numeric doses/rest
are finite/nonnegative; a free dose without a number requires its own original note.
Groups specify rounds, first side, sequence, transition and rest boundaries.
Same-side-then-switch/all-rounds-then-switch require all members per-side;
member-each-side permits mixed unilateral/bilateral work. Any unilateral member
requires an explicit first side; bilateral-only requires null. Mixed/unknown
positions require an explicit transition at activation, not inferred safety.

Rest priority is another set → set rest; another side → side rest; another member
→ member rest; next round → round rest; exit → exit rest. Never sum competing
boundaries. Inapplicable terminal rest is zero; one round has no between-round
rest, bilateral-only has no side-switch rest. All-rounds-then-switch ends the first
side with side rest, not round rest. Fixed expansion examples live in
`tests/fixtures/070/group-execution-expectations.json`.

Schema validation covers shape; domain/services additionally enforce lineage,
cross-row uniqueness, side/order/rest consistency and content resolution. Imports
save only drafts and original bytes/rationale. Activation revalidates a token tied
to edit state, previous active revision, review and live image eligibility; one
transaction retains pins/assets, supersedes and updates the active pointer.

Portable exports contain `plan.json`, `evidence.json`, readable `evidence.md`,
`plan-response.schema.json` and deduplicated `assets/` with decoded suffixes.
`scope: plan_revision` is not performed work. `scope: training_session` includes
frozen prescription/occurrences/results/batches/events/feedback, prior-plan/session
context and images. JSON and Markdown agree; missing historical assets are explicit.
Files/registration roll back together. Original older files are never rewritten.

## 3. Eligibility, Execution And Lifecycle

Selection, enablement, activation and start share complete text, valid required
images and no removal. Image inspection checks containment/hash/decoding/dimensions;
review binds exact content/image hashes separately. Missing/changed bytes invalidate
effective readiness without erasing original events or current stored intent.
Copy/edit creates unreviewed content, not inherited approval.

Execution freezes member/round/side, dose/rest/transition, content/assets and separate
activation/start review. Unilateral actions expand to distinct sides. Completed
means prescription-confirmed dose only; partial/exceeded require entered actuals;
unknown/not-completed do not invent actuals. Current actuals have explicit side.
Zero, unknown and original text remain distinct.

Commands check session version under a writer transaction. Round tokens freeze
exact unrecorded members at the displayed position, including both sides only when
the chosen sequence does. Save does not auto-advance; navigation is not performance.
Retraction audits original result/sets/notes and clears only its batch or individual
membership. Paused/terminal sessions reject result writes; terminal note corrections
are append-only with stale-value checks. Resume reads frozen evidence; new starts
recheck live eligibility. Feedback derives only performed main areas without defaults.

Removal freezes request reason/content/reference impact and appends decisions:
requested → under_review → approved → applied, or rejected/cancelled. A changed
target requires a new request; changed impacts require refresh and confirmation.
Apply rechecks transactionally and retains evidence; no variant/history cascade.
Publisher withdrawal is distinct from root-local decisions; observations do not
invent publisher timing. Restore validates current content/images but neither
enables nor repairs invalidated active-plan pins; new revision confirmation is needed.

## 4. Supported Old-Root Mapping

At 0.7.0, retained application endpoints were 0.6.0/schema14,
0.6.1/schema16 and 0.7.0/schema22. This mapping is historical as of 0.7.2.
The schema16 mapping below follows required earlier steps for the supported schema14
endpoint; absent historical review snapshots remain unknown. Intermediate schemas
are internal historical steps, not extra application releases. R2 implemented
pre-write refusal for expired roots and retired obsolete entry paths on 2026-09-21.
Schema1/9 positive tests were historical coverage; 0.7.0 tests rejected
schema1/9/13 unchanged and exercised the then-oldest retained schema14 conversion.

| Original fact | Current destination / preservation |
| --- | --- |
| Known bundled key, even renamed | Same namespaced key; local text/aliases/guidance are overrides, not package edits. |
| Unknown/missing bundled key | Distinct deterministic custom identity, original ID/key/text retained; no guessed name merge. |
| Selected/all referenced guidance | Immutable snapshots/overrides with exact JSON/revision and old review metadata. New hashes do not become historical facts. |
| Images/review answers | Preserve original bytes/hashes; stage retained assets with recovery. Missing/corrupt originals remain honest evidence, not eligible assets. |
| Plans and doses | Status/IDs and single-item doses retained; pins labelled migration-time rather than invented activation-time facts. Unknown side/rest fields stay unknown. |
| Sessions, actuals, events, audits | Use recorded historical guidance/name/areas/phase/rest/note/dose, retain IDs and before-images; NULL/false/true and zero/unknown remain distinct. |
| Old per-side aggregate work | One `per_side_aggregate` occurrence, no fabricated left/right counts. Existing results/timestamps/notes preserve unknowns; later actual entry explicitly chooses scope. |
| Feedback/import/export | Preserve original IDs/files/reasons/source and unanswered values; new export IDs exceed the old namespace. Normalize separators for lookup only. |
| Settings/enablement | Preserve meaningful root/locator and intent; missing-image use becomes ineligible. Unknown original fields remain read-only provenance. |

Strict v2 new imports cannot claim internal conversion provenance. Editing a
converted plan validates its stored identity/scope and preserves untouched unknowns.
Exported migration-bearing `plan.json` is evidence, not an importable response;
the separately supplied response schema governs new prescriptions.

## 5. Recovery And Entry Routing

`convert_catalog_root` handles a supplied root only. `UpgradeRecovery` owns an
exclusive OS lease; normal database connections hold shared leases. Snapshot via
online SQLite backup plus configuration/resources (including committed WAL facts)
is hash-verified; old backups/locks/journals/transient sidecars are excluded.
Unknown files survive; linked resources are rejected. Converter/validator operate
on a disposable work root, then publish validated facts/assets.

Internal `training_feedback.upgrade-recovery` v1 uses a root journal and
`backups/upgrade-v1-<id>/manifest.json` plus `snapshot/`. Prepared → publishing →
complete is successful. Interrupted prepared/publishing/restoring phases restore
the verified consistent snapshot, record rolled_back and may retry. Corrupt
snapshots block restore before live writes. Pending/malformed journals block normal
open. Restore is restartable; completed conversion is idempotent. Retain recovery
evidence; internal snapshots are not normal complete-root backups.

Bootstrap/root switching convert before opening `LibraryContext`, surface actionable
errors and save locator only after successful preparation. Switching constructs the
new window before committing locator and releasing the old context. Open sessions
must pause first; same-path switch is a no-op. No old UI/runtime compatibility mode.
Expired/future rejection precedes mutation. R2 introduced the then-schema14
lower-bound guard and retained-endpoint coverage on 2026-09-21; the current
support mapping is in the [version index](../history/README.md).

## 6. Frozen Fixtures And Verification

The schema16 root, preservation facts and fixture metadata were synthetic bytes
frozen from the pre-retirement runtime. They rotated to the untracked local
`docs/archive/0.6.1/` holding area in 0.7.2 and remain recoverable in Git history.
The fixture and its preparation helpers are no longer current test inputs.
R1 completed DB tracking and byte-preserving Git attributes on 2026-09-21;
clone and ZIP archive comparisons preserved 14/14 frozen files.

`packaging/prepare_contract_baseline.py <new-empty-directory>` was the historical
pre-illustration generation command and remains only in dated history. 070-H2-TESTS
retired the script and its executable test dependency. The contract test now checks
the frozen inventory and v1 schema bytes/structure directly, then independently
checks the current source, manifest, payload bytes and SQLite content. Never rewrite
a historical baseline to equal today's content.

Preserve original inputs and compare logical records/resources after supported
synthetic conversion, including SQL/file publication failure boundaries. Actual
identified retained binaries opening/closing baselines are required for public H3
packaged-upgrade acceptance only. H3 is deferred until an explicit public-release
request; source fixtures remain synthetic and do not become old-binary evidence.

Run focused tests within the [development workflow](../development-workflow.md)'s
budgets. Candidate hashes and
execution results belong to versioned local evidence; remove expired-version-only
fixtures together with migration entry support, not by deleting active dependencies.
