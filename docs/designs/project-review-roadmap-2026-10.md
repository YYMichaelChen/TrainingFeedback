## 1. 版本顺序与分配理由

| 计划版本 | 主题 | 原审视项序号 | 顺序理由 |
| --- | --- | --- | --- |
| `0.8.22` | 事务与更新退出保护、错误诊断 | 1、2、4、9 | 先收敛失败后的连接状态、未保存输入和多实例更新任务风险，为后续文件操作提供可用诊断 |
| `0.8.23` | 完整备份、后台文件操作与有界导入 | 3、6、10 | 统一考虑数据库与附件一致性、复制过程、完成边界和大文件读取，避免分别修改产生新的不一致 |
| `0.8.24` | 计划编辑体验与职责整理 | 7、8、11、12 | 先整理编辑状态，再补差异展示、修改识别和撤销；保持保存、启用、训练事实的边界 |
| `0.8.25` | 长期读取效率与维护配置 | 5、13、14、15、16 | 在可靠性与日常输入问题之后处理随历史增长的开销、重复启动检查及配置／文档漂移 |

四期均在现有桌面产品、数据根和训练模型内修复或增量完善，采用补丁版本；
不因本次审视建立新的平台、外部合同或正式兼容基线。它们是有独立交付目的的范围，
不是增加验证额度的划分。实际合并实施的同一次更新必须共用同一验证 scope。

默认按上述顺序推进，每次只打开一个活动 release PLAN；前一期如有被后一期依赖的
未完工作，应先解决或明确调整范围，不把未实施条目记为完成。版本号分配不自动授权
构建、提交推送或 GitHub Release 发布；分发时遵循[开发流程](../development-workflow.md)。
如紧急修复先占用预留版本，实施前更新本文及路由，不覆写已有分发版本身份。

| 原序号／优先级 | 静态依据与触发条件 | 目标与完成条件 |
| --- | --- | --- |
| 1／P1：提交失败回滚 | [统一事务](../../src/training_feedback/data/database.py)的 `commit()` 在异常处理分支之外；提交自身抛错不会进入当前回滚分支 | 提交失败也进入事务收敛；保留原始异常，明确回滚失败后连接是否可继续使用。复核调用方恢复与附件清理，避免把失败动作残留在后续事务中 |

| 4／P2：统一诊断 | [错误映射](../../src/training_feedback/error_messages.py)仅在未识别分支保存简单诊断，已翻译异常可能留下旧诊断；[入口](../../src/training_feedback/main.py)缺少覆盖启动组装的统一处理 | 启动和操作异常都保留对应时间、操作、版本与异常链；中文正文简洁，诊断可复制且有容量／保留边界。默认不记录完整计划、训练备注或审核原件，诊断失败不覆盖原错误；启动失败不能继续使用半初始化上下文 |
| 9／P2：活跃更新目录 | [临时目录清理](../../src/training_feedback/application/release_updates.py)按名称和内容识别目录，未证明所属任务已结束 | 用任务租约或等价的进程存活协调区分活跃与遗留目录；另一实例下载、等待退出或安装时不得被清理。保留已有精确目录归属与非链接限制，不扩展清理范围 |

实施顺序：事务收敛 → 诊断入口 → 更新关闭协调与任务租约。更新流程须明确区分
“下载完成但仍可继续编辑”和“已交接退出”；不能先启动看门狗，再等待用户处理表单。

实施时同步的权威位置：产品规范 §9.1 更新流程、§12.11 中文异常呈现；
实际源码、验证与候选事实按开发流程记录到对应版本历史。

## 3. 0.8.23：备份与文件输入

| 原序号／优先级 | 静态依据与触发条件 | 目标与完成条件 |
| --- | --- | --- |
| 3／P1：备份完成边界 | [备份实现](../../src/training_feedback/data/backup.py)直接复制到最终目录；进程中断可留下部分数据。数据库在线备份和附件遍历没有共同的多写入者快照边界 | 将部分副本与可恢复备份明确区分，完成后才发布最终目录；数据库引用与附件来自一致的逻辑状态。中断残留不得被普通打开流程当作完整备份，失败清理只处理本次拥有的输出，不覆盖目标或源数据 |
| 6／P2：文件操作响应 | [设置页](../../src/training_feedback/ui/settings_page.py)在界面线程同步调用完整备份 | 备份由应用层协调，界面显示进行中、完成或失败；耗时复制不占用界面线程。工作线程自行管理 SQLite 连接，不能直接搬用主线程连接；有取消入口时，取消不能发布为完成 |
| 10／P2：有界导入 | [计划导入](../../src/training_feedback/data/group_plan_handoff.py)整文件读取；[审核附件](../../src/training_feedback/data/review_attachments.py)读完后才检查 8 MiB 限制 | 读取过程即受限；审核附件沿用既有上限，计划文件按实际格式明确合理字节／结构边界。超限给出中文原因且不保存部分计划，不截断用户原文；保留严格 JSON、原件和预览确认语义 |

备份设计必须先决定对其它写入者的协调方式，再实现后台复制；仅把现有函数放进
线程不构成一致性修复。避免在持有同一连接写事务时直接调用会等待该事务的备份路径。
暂存目录的命名、可打开性和最终发布方式应一起设计；若使用完成标识，所有打开入口
必须有一致解释。更新下载和备份使用各自拥有的目录，不能互相套用清理权限。

实施时同步的权威位置：产品规范 §7 备份／恢复、§4.6 与 §12.8 外部文件边界；
没有存储格式变化时不增加 schema。需要改变持久格式或旧程序的打开边界时，先明确
相应版本变化及拒绝策略，再实施，不能把不兼容语义藏在附加 JSON 中。

0.8.22 的关闭协调，不另外维护一套绕过保护的流程。

实施时同步的权威位置：产品规范 §4.1 和 §12.11；所有新交互是拟议改进，实施前

## 6. 身份、验证与交付边界

- 四期预计只提升应用补丁号，沿用 schema `26`、编辑格式 `2`、contract `5`、
  catalog `070-illustrated-3`。这是设计目标，不能代替实施时对 DDL、持久格式、
  外部 wire schema 和根打开边界的实际判定；需要变化时在同一版本同步身份及映射。
- 当前支持根入口不因规划自动扩大或收缩；不扫描、打开、迁移或修改旧项目／真实
  用户数据库。未知不补零，用户文字不裁剪，完成训练冻结事实不重算。
- 本清单包含确定的代码结构／文案问题、需要特定条件触发的风险和可选体验增强。
  实施前针对所选条目复核源码与需求；尚无触发条件的风险不宣称已复现，撤销等新体验
  不宣称是现有功能故障。各表“完成条件”是实现与代码审查目标，不是运行验收清单。
- 严格按产品规范 §9.1 与测试说明执行：每次更新无具体启动失败风险为 0 项，有风险
  才选择最少相关场景，最多 3 项、通常 0～1 项；整次更新共用 scope，通过即停止。
  不预分配四套测试额度，不安排备份／导入／训练／性能功能回归或客户端自动操作。
- 人工测试默认 0 项；不追加完整流程、安装卸载、录屏或计时。版本、打包和收尾都不
  增加范围，未运行不是通过，也不是待补验收。发布不建立公共支持、外部内容审核、
  W4 或个人数据转移结论。
- 启动某一期实施时才建立唯一活动 PLAN，并将实际实现／版本身份与验证事实归入
  对应版本历史。跨期剩余项留在本设计并如实标记，不提前创建已发布历史条目。
