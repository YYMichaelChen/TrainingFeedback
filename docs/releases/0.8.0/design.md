## 目标与发布边界

v0.7.8 已先独立交付文档与知识治理修复。此后 v0.8.0 开发交付以下五项：卸载时可选择删除用户数据、安装时可选择程序目录、正式版前关闭旧版本兼容测试及支持承诺、清理项目冗余、以测量结果驱动应用级响应优化。剩余工作按下列顺序实现，不再预设其它 0.7.x 中间版；若后续确需独立可用的中间版，再按版本变更流程单独决定。方案本身不改变 schema/catalog/外部契约版本。

“正式版”由用户明确宣布。版本号到 0.8.0、制作本地安装包或完成本地验收，均不会自动宣布正式版或启动旧版本兼容义务。首个正式版建立基线；后续正式版在确有前序正式版本时，明确选定支持 **1 或 2 个旧正式版本**，以真实发布包和合成数据根验证；选定范围写入当时的版本支持表。正式版前不运行旧版本升级/回归/安装兼容检查，也不承诺旧版数据根能在新版打开。当前已有兼容代码在审计删除前可能仍可工作，但不构成承诺。所有阶段均须对未知/不支持数据根先校验再写入，拒绝时原目录不变；不扫描旧项目数据库。

## 1. 安装目录选择

现状：Inno Setup 脚本已有默认目录 `%LocalAppData%\Programs\TrainingFeedback` 和固定 `AppId`，未显式固定目录页显示方式。Inno 文档说明目录页受 `DisableDirPage` 控制，同一应用的旧安装目录可由 `UsePreviousAppDir` 作为默认值（[页面条件](https://jrsoftware.org/ishelp/topic_wizardpages.htm)、[旧目录规则](https://jrsoftware.org/ishelp/topic_setup_usepreviousappdir.htm)）。

实施：

1. 将目标目录页明确设为交互安装始终可见，保留上述默认目录及每用户安装权限；升级时预填现有安装目录。安装界面显示最终程序路径，允许浏览或输入其它目录。静默安装沿用 Inno 的 `/DIR` 机制和其现有语义，不增加数据根参数。
2. 安装前校验目标：不得是盘符根、Windows/Program Files 系统目录、选中/已知数据根或其父子路径，也不得复用有无关文件的目录。对路径规范化、大小写、尾随分隔符、UNC、重解析点和权限失败做明确处理；应用二进制始终与数据根分离。目录实际路径再次在写文件前校验。
3. 同一 `AppId` 的原位升级沿用旧目录。若用户主动改到另一目录，先明确旧目录与快捷方式的处理方案，保证只有一个有效启动入口；不得把旧目录内未知文件当作安装器所有物删除。取消安装不改 locator/root；失败安装可恢复或明确报告不完整状态。
4. 构建清单记录实际 `{app}` 位置无关的相对 payload 与 hash；验证自定义路径下快捷方式、卸载入口、重装与卸载都指向当前安装。

验收（开发者手动操作安装器；自动测试只验证脚本/路径规则）：

- [ ] 首次安装可选包含空格和中文的非默认目录，启动及快捷方式均从所选目录运行。
- [ ] 默认路径和原位升级正确；升级更改路径后无陈旧快捷方式/重复有效安装。
- [ ] 取消、不可写/非法/与数据根重叠路径被安全处理，locator 与合成数据根逐字节不变。
- [ ] 安装、卸载及重装不因程序路径变化而隐式重置数据根。

## 2. 可选用户数据卸载

现状：Inno 已提供普通程序卸载器；locator 仅记最后选中的一个数据根，不保存所有历史数据根。默认卸载只移除程序文件。卸载脚本可使用 [卸载事件](https://jrsoftware.org/ishelp/topic_scriptevents.htm) 展示选择与执行清理；Inno 对递归通配删除有明确风险提示（[UninstallDelete](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm)）。

范围决策：只对当前 locator 指向且经验证为 TrainingFeedback 的**一个**数据根提供删除选项，并同时可删除该 locator；其它曾选过的根、外部备份、导出到根外的文件均不发现也不删除。当前 locator 不记录全部历史根，因此扩大到“全部历史数据根”须另行设计可信登记机制和生命周期；不得靠扫描磁盘推断。

实施：

1. 卸载界面默认不勾选“删除我的数据”。未勾选时只删除安装器拥有的程序文件/快捷方式，保留 locator、根与备份；取消卸载亦不碰数据。
2. 勾选后显示完整规范化路径、预计删除内容（数据库、图片、备份、导出等根内文件）和不可恢复提示，并再次要求明确确认。无有效 locator、marker/config/schema 校验失败、根正在使用、路径与程序目录或用户主目录等危险范围重叠、路径含重解析点/连接、权限无法确认时禁用数据删除并显示原因；仍可仅卸载程序。
3. 删除实现由独立且可测试的应用/数据层辅助逻辑拥有路径验证和删除清单；Inno 只传递明确选项并调用受控逻辑。不得用宽泛通配符或 `UninstallDelete` 对 locator 中的字符串直接递归删除。执行前重新核验同一目录身份，防止选择后路径替换；只允许本用户数据根。先安全处理应用关闭/数据库连接，再执行删除。失败时报告实际保留路径与清理状态，不谎称“全部已删除”；设计可重试的中断记录，不把部分删除伪装成完整根。
4. 需要重新安装/恢复备份时，通过现有“打开已有数据根”流程；安装器不创建或迁移根。外部备份不在卸载器删除范围内。清理 locator 仅在数据根删除完成且确认属于本应用之后进行，以免删除失败时失去指向剩余数据的线索。

验收：

- [ ] 默认卸载/取消卸载后合成根、locator 和外部备份逐字节不变；程序文件及当前快捷方式按预期移除。
- [ ] 勾选并二次确认后只删除界面列出的确切合成根及 locator；拒绝确认后不删除数据。
- [ ] 无效 marker、根外路径、程序目录、用户主目录、符号链接/目录连接、打开中的根及权限失败均不会越界删除；记录保留的路径与可重试状态。
- [ ] 重装后能直接打开仍保留的根；卸载行为不被当作旧版本兼容测试。

## 3. 正式版前后的兼容边界

前正式版：关闭“旧应用版本升级”作为发布门槛的代码测试、合成旧版根测试、旧安装包安装测试和手动客户端检查。当前版本的新建根、同版本重启/重装、读写事务、未知/未来格式的只读拒绝及失败回滚仍按受影响风险测试；这属于当前数据安全，不是旧版兼容验收。若主动变更 schema/外部 wire schema，仍同改至少提升应用补丁版本，写明新根格式；不为了旧根保留迁移通道。旧根不因不受支持而被改写或删除。

正式版宣布时：用户确定首个正式版基线，固定其应用/schema/契约映射及真实二进制。后续正式版在存在前序正式版本时选择支持其中 1 或 2 个，建立合成根与到期策略，保留选定升级路径并运行代码级及独立安装兼容场景；过期/未来根先验只读拒绝。历史开发候选版不会自动变成受支持正式版本。若正式版声明与本地候选不同，必须对正式候选重新取得证据。

文档执行：同步修改开发计划、开发流程、测试说明、安装验收手册、版本索引和 AGENTS.md。历史 0.7.x 证据按当时规则保留事实，不倒填新政策、不把过去的 `not run` 改为 `pass`。正式版前的版本索引可标识“当前已实现读取路径”，但不得写成支持承诺。不同版本的历史文档清理需先提取仍生效的规则，保留 Git 可追溯性。

## 4. 项目瘦身

先固定可重复基线：`git ls-files` 的文档/源码/测试数量与字节数、安装 payload 文件数与大小、构建耗时、启动与常用页面响应基线。逐项建立“引用者—责任—保留/迁移/删除”清单，给出删除前后差值，不以文件数下降替代质量判断。

1. **文档**：保留一份现行产品规则、一份流程、一份当前支持表及候选证据；将重复的历史说明压缩为索引/版本事实。已过期完整记录按仓库流程归档/移除，避免保留无上限本地副本。旧版证据不能冒充当前规则，必要的行为规则先升入当前开发计划。
2. **代码与资源**：用静态引用、入口清单、打包 manifest 和合成根测试识别无调用模块、重复 helper、过期资源及旧 fixture。仅在证据证明无当前入口后删除。特别审计旧 schema migration、一次性 reset、历史 import/导出通道；保留当前新根初始化和只读拒绝必需部分。禁止清理用户根、原始导出或 Git 历史。
3. **测试**：删除仅验证已退役旧版本承诺且无现行安全价值的用例；保留当前事务、回滚、根隔离、未知格式拒绝、完整目录包及卸载路径安全覆盖。记录测试范围变化和预算，不通过拆分 scope 规避上限。
4. **打包**：核对 PyInstaller/Inno payload 的运行必需性，删掉源码内已无引用或打包中重复的大文件。每次清理后比对 manifest，构建与当前功能回归成功才算完成。

每个删除批次独立可回退；交付清单列出被删文件、引用检查、影响版本/契约及前后体积。若某项用途不明，保留并记录，不以猜测清理。

## 5. 应用程序级响应优化

用 Windows 上的隔离合成根测量：启动到可操作主窗口、已有根重启、根切换、目录创建、目录/计划/历史首次显示与刷新、搜索输入后更新、保存动作完成、备份；记录 p50/p95、最大 UI 无响应间隔、数据规模、机器/构建和冷/热启动条件。先找最长主线程阻塞和重复工作，再设置每条关键路径的改进目标。目标至少包括：确认的热点 p95 比基线下降 30% 或给出不可改善原因；常用交互不出现超过 200 ms 的无反馈主线程停顿；保存仍保持事务正确。任何数字需在同机同数据集重复测量并在方案实施阶段锁定样本量，不能用合成数据外推真实用户体验。

优先路径：

1. 建立低开销分段计时，只记录操作类别、耗时和数据规模，不记录用户文本、路径或个人内容；默认不持久化敏感诊断数据。
2. 减少启动/切根时重复读取与对象重建；优化 SQLite 查询与索引需先看查询计划，不能改变用户事实、排序或时间边界。
3. 对目录渲染、搜索和图片解码做增量/分页/缓存；缓存按根、catalog、内容版本及修改事件失效，避免跨根混用或陈旧显示。
4. 把纯读取、图片处理及可取消的长任务移离 Qt 主线程；数据库连接只在拥有线程使用。Qt 主线程更新控件；写操作仍由应用层协调并保持一次用户动作的事务语义，取消不留下半写入。
5. 对启动、频繁页面切换、保存失败、切根和关闭做回归；错误/长任务给出可见状态与取消反馈。开发者手动检查真实 UI 流畅度；禁止用 GUI 自动化代替。

验收交付基线与对比表、测量脚本/样本描述、针对热点的代码改动、必要的性能回归阈值和正确性结果。若基线不支持“明显变快”的结论，只报告客观测量并继续定位瓶颈。

## 实施顺序与发布验收

1. **规则与基线**：落实兼容政策、卸载范围、安装路径安全规则；测量仓库和响应基线。此步不升版本。
2. **安装/卸载**：先做可测试的路径和清理逻辑，再接 Inno 页面/卸载事件；用隔离合成根覆盖默认、选中、取消、故障、重装与自定义目录。
3. **瘦身**：按清单小批删除，先转存仍生效规则，再移除旧兼容入口与冗余文档/资源；每批验证当前功能和打包。
4. **响应优化**：按测得瓶颈排序，逐项改动、对比和回归；不预设一定使用线程或缓存。
5. **v0.8.0 合并与验收**：一次完成应用版本、版本索引、源码/测试/打包一致性检查；按 minor release 的单一 pytest scope 选取受影响风险。构建干净源码的本地候选，核对完整 payload/hash，并由开发者手动操作已安装客户端。正式版前不跑旧版兼容场景；未手测项如实写 `not run`。公开发布、个人数据转换、内容审查与 W4 均有独立门槛，本版完成不自动触发。

本方案批准前的代码级与客户端结果互不替代；每个候选只引用其精确构建的证据。最终 `0.8.0` 只有在五项实现、受影响测试、安装/卸载手测和响应对比完成后才可声称完成。此方案中的可勾选框为**未来开发者手动验收任务**，当前均未运行。
